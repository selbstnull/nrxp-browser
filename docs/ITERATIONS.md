# ITERATIONS — план разработки netrunner-browser

Это **рабочий файл**: разработка ведётся строго по нему. Архитектура — [ARCHITECTURE.md](ARCHITECTURE.md),
факты и источники — [research/NOTES.md](research/NOTES.md), журнал выполнения — [PROGRESS.md](PROGRESS.md).

## 0. Приоритет

> **Сначала — чтобы рендерило, работало и открывало сайты. Потом — туннель. Потом — узлы и деплой.**

Поэтому I1–I3 идут по системной сети (без NRXP): это даёт рабочий браузер раньше всего и отделяет
проблемы движка от проблем транспорта. Туннель (I4–I5) подключается к уже работающему браузеру.

## 1. Правила файла (как вставлять промежуточные этапы)

* **ID стабильны, нумерация не сдвигается.** Новый этап между `I5` и `I6` называется `I5.1` (затем `I5.2`…).
  Этап внутри этапа, который стал слишком большим, — `I5.a`, `I5.b` с общим родителем. Существующие ID не переименовываются.
* Вставка = (1) добавить секцию по шаблону §2 в нужное место, (2) обновить строку в таблице §3,
  (3) поправить поле «Зависит от» тех, кого вставка затрагивает, (4) записать причину в §9 «Журнал изменений плана».
* **Спайк** — этап вида `Ix.s`, цель которого «да/нет» за 1–2 дня; результат фиксируется в `research/NOTES.md`,
  а следующий этап читает его вывод. Если спайк отвечает «нет» — план правится до начала зависимых этапов.
* **Статусы:** `todo` · `doing` · `done` · `blocked` · `dropped` (с причиной). Статус меняется только вместе с записью в PROGRESS.md.
* **Definition of Done для любого этапа:** (а) все пункты «Приёмка» выполнены и их вывод/команды записаны в PROGRESS.md;
  (б) `cargo fmt --check`, `cargo clippy --workspace -- -D warnings`, `cargo test --workspace` зелёные (для крейтов без Servo
  — всегда, для Servo-сборки — на последнем кэшированном билде); (в) коммит(ы) в `main` с ID этапа в сообщении (`I2: …`);
  (г) если этап менял протокол/соседний репозиторий — отмечено в «Координация» и не запушено без решения владельца.
* **Не пушим в `netrunner-proxy`/`nrxp-smoltcp`/сторонние репозитории без явного решения владельца** — там уже есть
  непушенная работа (см. PROGRESS.md «Координация»).

**Итог (факты, 2026-10-07):** `nrb snap` работает; example.org, Wikipedia (Rust), Hacker News рендерятся корректно (кириллица, RTL-арабский, CJK, SVG);
`http://127.0.0.1:1/` → код 4 (кадр пустой — Servo рисует свою страницу ошибки), без паники. **Известные дефекты (в корпус I3):**

**Итог (2026-10-07, debug-сборка Servo 0.7.0, системная сеть, 57 сайтов, 12 категорий):**
ok **40/57 (70%)**, **открылось (ok+partial+signature_miss) 51/57 (89%)**; после вынесения 8 известных нерабочих — ok 38–40 из 49 (78–82%), открылось 95,9%.
Воспроизводимость статусов между прогонами 91,2% (52/57). Ratchet проверен: 77,6% < baseline 78% → exit 1.
**Что нашли:**
* Штатный скриншот Servo ждёт «полной готовности»; у ~10 живых сайтов (GitHub, BBC, NYT, Habr, Tailwind, Discord, Microsoft, Vercel…) она не наступает →
  введён статус `partial` (кадр из того, что уже нарисовано): без него «открылось» было бы 61%, с ним 89%.
* Реальные несовместимости: `react.dev` — «Application error: a client-side exception» (JS-сбой); GitHub — исключение в react-dom, страница рисуется, но часть
  SVG-иконок (логотип) пропадает; Wikipedia — SVG-маски как чёрные квадраты; `yandex.ru`/`amazon.com` — пустой кадр.
* Антибот: stackoverflow (Cloudflare «Just a moment…»), ebay («Pardon Our Interruption») — фиксируем как known-broken.
* **Краш:** `nytimes.com` иногда падает — `StyleThread#1 has overflowed its stack` (debug-сборка; нужна проверка на release, I13/I14).
* Среда: порт 80 (plain HTTP) недоступен из этой сети (neverssl) — не дефект браузера.

Воспроизведение: 16+ одновременных открытий. Для браузера (десятки соединений за раз) это постоянная потеря соединений. Исправление — **патч в ядре** (`patches/proxy/0001-fix-muxer-Connect.patch`, локальная ветка `nrb/connect-reliable` в отдельном worktree `.nrb-dev/netrunner-proxy`, **не запушено**). После патча 200 параллельных потоков × 3 прогона — стабильно.

### I5.s — Спайк S3: reverse-egress
Статус: done (2026-10-07, вердикт по коду; прототип — первая задача I9) | Зависит от: I4
**Цель** — ответить «да/нет», можно ли в ядре сделать так, чтобы дозвонившаяся сторона обслуживала потоки, а принявшая — открывала их.
**Что смотреть** — `ServerHandler::run`, `ClientHandler::connect…`, `Muxer::new(is_client, …)`, чётность `stream_id`, роли хендшейка vs роли потоков, `NodeMesh`/`MeshPeerSession` (`core/src/net/mesh.rs`, `connection/connection.rs`).
**Приёмка** — игрушечный стенд (2 процесса + netns): A набирает B, B открывает поток к loopback-эхо на стороне A; вердикт и список правок ядра — в NOTES.md. Если «нет» — план I9 переписывается на UPnP/IPv6/hole-punch.

**Итог (2026-10-07): ДА, reverse-egress реализуем без смены протокола.** Основание (чтение `core/src/net/connection/{connection,engine,handler}.rs`):
* Роль данных определяется не направлением хендшейка, а тем, что передано в `TunnelEngine`: и клиентская (`connection.rs:~1719`), и серверная (`~2970`) стороны строят один и тот же `TunnelEngine { handler: StreamHandler::new(muxer, opener) … }`.
  Серверная роль = `opener: Some(RemoteOpener)` (открывает цели на входящий `Connect`); клиентская = `opener: None`. Реконнект есть только у стороны с непустым `remote_addr` (дозванивающейся) — для egress за NAT это правильно.
* Следовательно «egress за NAT» = дозванивающийся (клиентский хендшейк, реконнект) **с `opener`**, а принимающий ingress (серверный хендшейк) — **без `opener`**, но с возможностью *порождать* потоки поверх этой сессии.
**План правок ядра (для I9, ~4 патча, без смены wire-формата):**
1. Вынести из `ClientHandler::connect…` цикл «RawCast-кадры приложения ⇄ потоки muxer» (`connection.rs ~1860–2300`) в `spawn_rawcast_bridge(muxer, rx, tx, …)` — чистый рефакторинг; им же будет пользоваться ingress поверх принятой сессии.
2. `ClientHandler::connect_as_egress(addr, sni, token, identity, opener_policy)`: как `connect`, но движки ног получают `StreamHandler::new(muxer, Some(RemoteOpener{…}))`.
3. Сервер: новый префикс токена (`egress:` рядом с `mesh:`/`mesh4:`) → после проверки `opener = None`, `Muxer` кладётся в реестр `ReverseEgressRegistry` (ключ — `node_id`/пользователь), сессия не удаляется по `SESSION_CLEANUP_DELAY`, пока жива.
4. Маршрутизация: `RemoteOpener::open_tcp…` на ingress, если для пользователя есть reverse-egress — не открывает цель локально, а открывает поток поверх reverse-сессии (тот же путь, что у mesh-пира `MeshPeerSession`) и мостит байты.
**Риски:** авторизация регистрации (секрет узла/`LocalAuth`), политика «кому можно выходить через мой egress», отзыв, учёт трафика/квот на двух сторонах, поведение при падении reverse-сессии посреди потока (потоки закрываются, как при потере ног — см. сторож в `NrxpTransport`).

и сквозной `scripts/node-e2e.sh` (3/3 прогона): init → run → invite → pair → fetch через узел == curl → ссылка в `--node` → чужой токен отвергнут → **сканер видит decoy** → **`snap` страницы через свой узел** → revoke → отозванный отвергнут → штатная остановка.
**Найдены и исправлены:** (1) *гонка реестра устройств* — кэш перечитывался не чаще раза в секунду, а обход отзыва сбрасывал этот таймер → подключение сразу после `invite` отвергалось по пустому реестру (регрессионный тест `invite_issued_right_after_a_sweep_is_accepted_immediately`); теперь проверка `stat` на каждой валидации; (2) `--node 'nrxp://…'` в `snap`/окне не обрабатывалась и печатала ссылку с секретами в ошибке.
**Известные ограничения:** проверка на loopback, не в netns; узел не фильтрует цели клиентов (loopback/private разрешены — клиент спаренного устройства доверенный; для чужих клиентов нужна политика, I9); квоты не поддерживаются; приглашение содержит общий секрет узла (отзыв устройства закрывает только токен, смена секрета — отдельная операция, не сделана).

### I8 — `nrb deploy` на VPS
Статус: done (2026-10-07; проверено только на тестовом контейнере, не на реальном VPS) | Зависит от: I7
**Цель** — одна команда ставит ingress на чистый сервер и возвращает рабочее приглашение.
**Задачи**
- [x] `crates/nrb-deploy` на `russh` (системный `ssh` не нужен; **без SFTP** — заливка потоком через `cat > файл` в exec-канале, меньше зависимостей)
- [x] Аутентификация: ключ (по умолчанию `~/.ssh/id_ed25519`/`id_rsa`, passphrase из `NRB_SSH_KEY_PASSPHRASE`) или пароль (`--password-env` / запрос без эха; только для этого сеанса). **Отпечаток хоста**: сохранённый пин → иначе вопрос в терминале (в неинтерактивном режиме — отказ) → `--trust-host-key SHA256:…`; принятый пин запоминается в `known_hosts.toml` (свой файл, `~/.ssh/known_hosts` не трогаем); несовпадение пина = явное предупреждение о возможном MITM. **Не сделано:** установка ключа по паролю
- [x] Probe: ОС/архитектура, systemd, root или `sudo -n`, ufw, BBR, занятость порта, свободное место, уже стоящая версия и порт существующего узла; несовместимое — отказ **до изменений** (7 проверенных случаев)
- [x] Артефакт: `--binary <файл>` или `self`; архитектура ELF сверяется с `uname -m` сервера; sha256 после заливки; **запуск `nrb --version` на сервере до замены рабочего бинаря**. `scripts/build-node-musl.sh` → статический `static-pie` musl-бинарь 21 МБ. **Не сделано:** подписанные релизы и проверка подписи на сервере (→ I14), сборка под aarch64
- [x] Секрет и ключи генерируются **на сервере** (`nrb node init` от пользователя `nrb-node`); наружу — публичный ключ и приглашение (в журнале деплоя секретов нет — проверено)
- [x] Конфиг `0600`, юнит с усилением (отдельный пользователь, `NoNewPrivileges`, `ProtectSystem=strict`, `CAP_NET_BIND_SERVICE`, фильтр syscalls и др.; проверено, что systemd его применяет), `StandardOutput=null`; ufw (если активен) — порт TCP+UDP; `--bbr` — sysctl `bbr`+`fq` (если ядро умеет). **Не сделано:** nft/iptables/firewalld (только предупреждение), проверка внешнего файрвола провайдера
- [x] Проверка настоящим клиентом с локальной машины: временное устройство → NRXP-хендшейк и поток наружу (`example.com:80`) → устройство отзывается; провал хендшейка → откат; нет выхода в интернет — предупреждение
- [x] Идемпотентность: повторный запуск = апгрейд (ключи сохраняются, смена порта на месте отказана); `nrb deploy --remove`. Вывод без секретов
- [ ] → позже: установка без SSH (печать команды / docker-вариант)
**Приёмка** — на чистой VM/контейнере с sshd: `nrb deploy root@host` → клиент подключается и открывает сайты; искусственный сбой на шаге файрвола → откат без остатков; повторный запуск идемпотентен.

**Итог (2026-10-07):** `nrb deploy user@host --binary … [--node-port --public-host --device --trust-host-key --bbr --dry-run --remove]`. 19 юнит-тестов на поддельном сервере (порядок шагов, 7 отказов до изменений, откат чистой установки и апгрейда, битая заливка, бинарь не запускается, экранирование ввода, sudo, dry-run, ufw) и
`scripts/deploy-e2e.sh` на контейнере Ubuntu 24.04 с настоящим systemd+sshd (`tests/deploy/`; 25+ проверок): неизвестный/неверный отпечаток и отсутствующий ключ отвергаются, dry-run ничего не меняет, установка → служба от `nrb-node`, `node.toml` 0600, юнит применён,
**трафик через развёрнутый узел == curl**, апгрейд сохраняет ключи и старые устройства, **откат при сбое проверки** (апгрейд: прежний бинарь и служба на месте; чистая установка: следов нет), `--remove` убирает всё. Проходит и с glibc-, и со статическим musl-бинарём.
**Найдено сценарием и исправлено:** (1) явный `--trust-host-key` не запоминал пин; (2) проверка «служба активна» возвращала «нет» без dbus (не-root `systemctl`) → теперь через `sudo`; (3) порт 18443 хоста был занят моим старым dev-узлом (сценарий теперь падает сразу и понятно).
**Не проверено:** реальный VPS (другие дистрибутивы, провайдерский файрвол, медленный канал, IPv6-only), вход по паролю, ключи с passphrase, RSA-ключи, aarch64.

### I9 — Reverse-egress
Статус: done по ядру и CLI (2026-10-07); остаток — вставной этап I9.2 | Зависит от: I5.s, I7
**Цель** — домашний `nrb` за NAT выпускает трафик в интернет через ingress на VPS.
**Задачи** — по результату S3: ядро (смена ролей потоков на входящей сессии, вариант `MeshPeer` по handle сессии — **координация**), `nrb-node::Egress` (регистрация, heartbeat, отзыв), политики: только свои устройства по умолчанию, блок loopback/private/link-local/metadata, лимиты полосы/потоков, без логов трафика, kill-switch, явный режим `lan: allow`; UI включения с предупреждением; маршрутизация «выход через дом» на стороне клиента.
**Приёмка** — клиент B → ingress A (VPS) → egress C (дом): проверка внешнего IP показывает IP C; попытка достучаться до `192.168.*`/`127.0.0.1` через C блокируется; отключение C убирает его из маршрутов без обрыва остальных потоков.

**Итог (2026-10-07).** Сделано и проверено запуском:
* **Ядро** (`patches/proxy/0002-feat-core-reverse-egress.patch`, ветка `nrb/connect-reliable` рабочего дерева; **не запушено, нужен ревью владельца ядра**; wire-формат не менялся):
  `ClientHandler::connect_egress` (токен `egress:<метка>:<токен>`, `StreamHandler` дозвонившегося получает `RemoteOpener{mesh_peer:true}` + `EgressPolicy`, только TCP-ноги, без датаграммной ноги);
  `ServerHandler::with_reverse_egress(registry)` — принимающий распознаёт префикс, проверяет **`AuthValidator::validate_egress`** (новый метод трейта, по умолчанию отказ: роль выдаётся явно), оставляет `opener = None` (дозвонившийся не может открывать потоки к ingress), кладёт сессию в `ReverseEgressRegistry`;
  `RemoteOpener::open_tcp_with_privacy` по `ExitMode` { `Local` | `Prefer` (нет выхода — локально) | `Require` (нет выхода — отказ, **без** выхода с самого узла) } открывает поток поверх сессии выхода (`bridge_via_peer` — вынесенный из `open_via_mesh` мост с кредитами); UDP при удалённом выходе отвергается.
  `EgressPolicy` по умолчанию режет loopback/private/link-local (в т.ч. метаданные облака)/CGNAT/multicast/unspecified, v4-mapped v6 канонизируется; адрес резолвится **на выходе** и подключение идёт к проверенному адресу (без повторного резолва — DNS-rebinding не обходит).
  9 тестов в ядре (поток 3 МБ через выход; require — fail closed; prefer — откат; закрытая LAN; дозвонившийся не открывает потоки к ingress; токен без роли не регистрируется; политика адресов); весь `cargo test -p netrunner-core --lib` — 251 тест зелёный.
* **`nrb-node`:** `Role { Client, Egress }` у устройства (токен одной роли не годится для другой; `devices.json` обратно совместим — по умолчанию `client`), `node.toml: exit = "local"|"prefer"|"require"`, `Egress::start` (ждёт ногу, различает «отвергнут» и «нет ответа»), `IngressHandle::live_egress`.
* **CLI:** `nrb node invite --egress <имя>`, `nrb node devices` показывает роль, `nrb egress <ссылка|конфиг> [--allow-lan] [--label]` (за NAT, без входящих портов; завершается, если токен отозван).
* **Проверки:** `crates/nrb-node/tests/reverse_egress.rs` (5 тестов: выход/отказ без выхода/закрытая LAN/роли/отзыв), `scripts/egress-e2e.sh` — три отдельных процесса `nrb` (клиент → узел → дом → цель), «всё прошло»: fail closed без выхода, роли, LAN закрыта по умолчанию и открывается `--allow-lan`, `https://example.org` через дом, остановка выхода не выпускает трафик с узла, отзыв убирает выход на лету.
**Не проверено / ограничения:** внешний IP «у дома» на одной машине не отличить — приёмка по IP нужна на двух хостах (узел на VPS + реальный дом); выход выбирается один на узел (последний подключённый), а не по устройству клиента; режим `exit` читается при старте узла (смена — перезапуск); нет лимитов полосы/потоков на выходе и учёта трафика выхода; режим `Prefer` при падении выхода посреди потока рвёт поток (как потеря ног); UDP через выход не поддержан (QUIC/h3 тут и так не нужны); один скомпрометированный токен выхода получает трафик **всех** клиентов узла в режимах prefer/require — токены выхода выдавать только своим устройствам.
