# ITERATIONS — план разработки netrunner-browser

Это **рабочий файл**: разработка ведётся строго по нему. Архитектура — [ARCHITECTURE.md](ARCHITECTURE.md),
факты и источники — [research/NOTES.md](research/NOTES.md), журнал выполнения — [PROGRESS.md](PROGRESS.md).

## 0. Приоритет

> **Сначала — чтобы рендерило, работало и открывало сайты. Потом — туннель. Потом — узлы и деплой.**

Поэтому I1–I3 идут по системной сети (без NRXP): это даёт рабочий браузер раньше всего и отделяет
проблемы движка от проблем транспорта. Туннель (I4–I5) подключается к уже работающему браузеру.

## 1. Правила файла (как вставлять промежуточные этапы)

* **ID стабильны, нумерация не сдвигается.** Новый этап между `I5` и `I6` называется `I5.1` (затем `I5.2`…).
  Этап внутри этапа, который стал слишком большим, — `I5.a`, `I5.b` с общим родителем. Существующие ID не переименовываются.
* Вставка = (1) добавить секцию по шаблону §2 в нужное место, (2) обновить строку в таблице §3,
  (3) поправить поле «Зависит от» тех, кого вставка затрагивает, (4) записать причину в §9 «Журнал изменений плана».
* **Спайк** — этап вида `Ix.s`, цель которого «да/нет» за 1–2 дня; результат фиксируется в `research/NOTES.md`,
  а следующий этап читает его вывод. Если спайк отвечает «нет» — план правится до начала зависимых этапов.
* **Статусы:** `todo` · `doing` · `done` · `blocked` · `dropped` (с причиной). Статус меняется только вместе с записью в PROGRESS.md.
* **Definition of Done для любого этапа:** (а) все пункты «Приёмка» выполнены и их вывод/команды записаны в PROGRESS.md;
  (б) `cargo fmt --check`, `cargo clippy --workspace -- -D warnings`, `cargo test --workspace` зелёные (для крейтов без Servo
  — всегда, для Servo-сборки — на последнем кэшированном билде); (в) коммит(ы) в `main` с ID этапа в сообщении (`I2: …`);
  (г) если этап менял протокол/соседний репозиторий — отмечено в «Координация» и не запушено без решения владельца.
* **Не пушим в `netrunner-proxy`/`nrxp-smoltcp`/сторонние репозитории без явного решения владельца** — там уже есть
  непушенная работа (см. PROGRESS.md «Координация»).

### I1 — Servo собирается и рендерит (headless → PNG)
Статус: todo | Зависит от: I0 | Спайки: S0 (собирается ли Servo на этой машине)
**Цель** — `nrb snap <url> -o out.png` загружает страницу через Servo по системной сети и сохраняет скриншот.
**Почему в этом месте** — это главный технический риск всего проекта (тяжёлая сборка, API встраивания). Пока его нет — всё остальное бессмысленно.
**Задачи**
- [ ] Спайк S0: поставить недостающие системные пакеты (по отчёту `check-env.sh`), собрать `servo = "=0.7.0"` (+ `default-features` по необходимости), записать время сборки и размер `target/` в NOTES.md
- [ ] `crates/nrb-engine-servo`: реализация `Engine` поверх `servo::{Servo, ServoBuilder, WebView, WebViewBuilder, WebViewDelegate}`; зависимость на Servo — **только** здесь и за фичей `servo` бинаря `nrb`
- [ ] Headless-рендер: программный `RenderingContext` (software/offscreen), без окна и дисплея; чтение пикселей `WebView` → PNG
- [ ] Ожидание готовности: `notify_load_status_changed(Complete)` + таймаут (`--timeout`, по умолчанию 30 с) + опциональная пауза/`--wait-for-idle`
- [ ] Размер вьюпорта `--size 1280x800`, `--scale`
- [ ] Коды возврата: 0 — снимок есть; 2 — таймаут; 3 — крах/ошибка движка; 4 — пустой кадр (все пиксели одного цвета)
- [ ] Установка `rustls` crypto provider (в примере Servo — `aws_lc_rs`; для узла нам нужен `ring` → зафиксировать решение в NOTES.md)
- [ ] CI-заготовка: скрипт `scripts/build-servo-cache.sh`
**Результат** — бинарь `nrb` с подкомандой `snap`; крейты `nrb-engine`, `nrb-engine-servo`.
**Приёмка**
- `nrb snap https://example.org -o /tmp/a.png` → 0, файл PNG 1280×800, есть минимум 2 различных цвета, различимый заголовок «Example Domain» (проверка вручную + проверка «не пустой»)
- то же для `https://en.wikipedia.org/wiki/Rust_(programming_language)` и `https://news.ycombinator.com`
- `nrb snap http://127.0.0.1:1/ -o x.png` → не 0, без паники
**Риски / что делать, если нет** — Servo не собирается (SpiderMonkey/clang) → фиксируем причину, пробуем `servo-fetch-cli`/готовый servoshell как диагностику; если принципиально нет — этап `I1.fallback`: оценка CEF/Chromium (решение владельца, архитектура допускает второй `Engine`).

**Результат** — первый отчёт совместимости; список «чего Servo не тянет».
**Приёмка** — `nrb corpus run` на чистой сборке заканчивается отчётом; повторный запуск воспроизводит ≥ 90% результатов (оценка флака).
**Риски** — сайты меняются (флак) → подписи делаем слабыми (заголовок), а не точными.

### I4 — NRXP-транспорт и `nrb fetch`
Статус: todo | Зависит от: I0 | Спайки: S4, S5 (см. I4.s)
**Цель** — Rust-код, который открывает потоки через NRXP напрямую (без TUN/root) и по ним качает HTTPS-страницы.
**Почему в этом месте** — самостоятельный слой; не зависит от Servo, поэтому можно вести параллельно с I1–I3 и тестировать без графики.
**Задачи**
- [ ] `crates/nrb-transport`: `trait Transport { open_tcp, open_udp, caps }`; `SystemTransport` (обычные сокеты, для тестов) и `NrxpTransport` (`netrunner_core::net::ClientHandler::connect` + `RawCastFrame`, как в `tools/loadtest`)

- [ ] `NrxpStream: AsyncRead + AsyncWrite` над парой `mpsc<RawCastFrame>`; `Close` → EOF; backpressure не ломаем (кредиты делает ядро)
- [ ] Конфиг узла: адрес, `decoy_sni`, `nrxp_secret`, `nrxp_public_key`, `auth_token` — файл + переменные окружения; формат совместим с тем, что отдаёт backend (`/nodes/routing`)

**Приёмка**

**Риски** — публичный API ядра может требовать приватных типов → правка соседнего репо, фиксируем в «Координация».

### I5 — Весь трафик движка через NRXP (режим P)

**Цель** — браузер открывает сайты **только** через NRXP; системная сеть не используется.

- [ ] Загрузки: перехват скачиваемых ресурсов, прогресс, каталог, «открыть папку» (**проверить**, есть ли в API Servo хук загрузок; если нет — перехват по `Content-Disposition`/MIME на уровне `nrb-net`)
- [ ] Настройки: поисковик, домашняя, UA, масштаб, тема, JS вкл/выкл по сайту, куки-политика
- [ ] Контекстное меню, поиск по странице (Ctrl+F), печать/PDF (если API позволяет), приватные окна (`private_resource_threads`)

- [ ] DevTools: флаг `--devtools <port>` (сервер devtools Servo)
**Приёмка** — перезапуск восстанавливает вкладки и логины; закладки/история переживают рестарт; файл скачивается и открывается; приватное окно не оставляет следов в профиле.

## 6. Этапы «узел и деплой»

### I7 — Узел: ingress в lib, LocalAuth, invite/pair
Статус: todo | Зависит от: I4, I4.s
**Цель** — `nrb node run --role ingress` принимает клиентов без бэкенда; клиент подключается по приглашению.
**Задачи**
- [ ] **Координация (соседний репо):** вынести `server/src/{network.rs,…}` в библиотеку (`netrunner-server-lib`), бинарь `netrunner-server` остаётся тонкой обёрткой; ветка в `netrunner-proxy`, **без push** до решения владельца
- [ ] `crates/nrb-node`: `Ingress` поверх `ServerHandler`; генерация `LocalIdentity` (секрет + X25519), strict-режим по умолчанию
- [ ] `LocalAuth: AuthValidator` — реестр спаренных устройств (токен ↔ id, квоты опционально), `report_node_health` no-op, `list_mesh_peers` из локального реестра
- [ ] Decoy: параметры `--decoy-host`/режим relay по умолчанию; проверка, что сканер видит обычный TLS-сайт
- [ ] `nrb invite` (одноразовый токен, TTL) → ссылка/QR `nrxp://host:port?pk=…&sni=…&token=…`; `nrb pair <invite>`
- [ ] Сборка `--no-default-features --features node` (без Servo/GUI), статический musl
- [ ] Менеджер узлов в GUI: список, статус, создать приглашение
**Приёмка** — в netns: узел A (ingress), клиент B спарен по приглашению → страницы идут через A; клиент без токена получает decoy-сайт, а не прокси; отозванный токен перестаёт работать; бэкенд не запущен.

### I8 — `nrb deploy` на VPS
Статус: todo | Зависит от: I7
**Цель** — одна команда ставит ingress на чистый сервер и возвращает рабочее приглашение.
**Задачи**
- [ ] `crates/nrb-deploy` на `russh` + SFTP (системный `ssh` не нужен)
- [ ] Аутентификация: ключ или одноразовый пароль (используется только для установки ключа, не сохраняется); **отпечаток хоста показывается и пинится** с явным подтверждением
- [ ] Probe: `uname -m`, дистрибутив, systemd, root/sudo, занятость порта, BBR/fq
- [ ] Артефакт: свой `nrb` (musl-узел) по SFTP, если архитектура совпадает; иначе подписанный релиз с проверкой ed25519 **на сервере**
- [ ] Секрет и ключи генерируются **на сервере**; наружу возвращаются публичный ключ и одноразовый токен
- [ ] Конфиг `0600`, systemd-юнит с усилением (`NoNewPrivileges`, `ProtectSystem=strict`, непривилегированный пользователь, `CAP_NET_BIND_SERVICE`), **без логов трафика на диск**; файрвол (ufw/nft) только порт узла; опционально sysctl `bbr`+`fq`
- [ ] Проверка: loopback `/health` + **настоящий NRXP-хендшейк с локальной машины**; провал → откат (стоп юнита, удаление файлов)
- [ ] Идемпотентность: повторный запуск = апгрейд; `nrb node remove <host>`; вывод без секретов в логах
- [ ] Альтернатива без SSH: печать команды установки / docker-варианта
**Приёмка** — на чистой VM/контейнере с sshd: `nrb deploy root@host` → клиент подключается и открывает сайты; искусственный сбой на шаге файрвола → откат без остатков; повторный запуск идемпотентен.

### I9 — Reverse-egress
Статус: todo | Зависит от: I5.s, I7
**Цель** — домашний `nrb` за NAT выпускает трафик в интернет через ingress на VPS.
**Задачи** — по результату S3: ядро (смена ролей потоков на входящей сессии, вариант `MeshPeer` по handle сессии — **координация**), `nrb-node::Egress` (регистрация, heartbeat, отзыв), политики: только свои устройства по умолчанию, блок loopback/private/link-local/metadata, лимиты полосы/потоков, без логов трафика, kill-switch, явный режим `lan: allow`; UI включения с предупреждением; маршрутизация «выход через дом» на стороне клиента.
**Приёмка** — клиент B → ingress A (VPS) → egress C (дом): проверка внешнего IP показывает IP C; попытка достучаться до `192.168.*`/`127.0.0.1` через C блокируется; отключение C убирает его из маршрутов без обрыва остальных потоков.

Статус: todo | Зависит от: I5, I4.s | Спайки: S2
