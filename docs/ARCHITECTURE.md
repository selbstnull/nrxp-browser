# netrunner-browser — архитектура v1 (черновик)

Статус: проект, кода нет. Дата: 2026-10-07. Заменяет v0 (там был стек Blitz + Boa — он отброшен, см. §3).
Пометка **[проверить]** — допущение, которое должен подтвердить или опровергнуть спайк из §11.

## 1. Что строим

Один Rust-бинарь `nrb`, который одновременно:

1. **браузер** — полноценный движок, весь трафик которого идёт только через NRXP (никакой сети ОС);
2. **узел сети NRXP** — может принимать чужих клиентов (**ingress**) и/или выпускать их трафик в интернет
   со своего IP (**egress**), то есть быть тем же, чем сегодня является `netrunner-server`;
3. **деплоер** — умеет по SSH поставить свой же узел на VPS пользователя, чтобы вынести ingress наружу.

```
 клиент (app / другой nrb)            VPS пользователя                  дом / ноутбук с браузером
 ┌────────────────┐   NRXP    ┌──────────────────────────┐  NRXP (исходящее  ┌──────────────────────┐
 │ packet/stream  ├──────────►│ nrb node: INGRESS        │◄──── соединение ──┤ nrb: EGRESS          │──► интернет
 └────────────────┘ (маска    │  decoy-fallback, auth    │  за NAT, reverse) │  (и браузер, и узел) │   с домашнего IP
                      TLS)    └──────────────────────────┘                   └──────────────────────┘
 Варианты: ingress+egress на одной машине; браузер с публичным IP — сам и ingress; цепочка через mesh.
```

## 2. Один бинарь, три режима, общее ядро

```
nrb                      GUI-браузер (+ опционально узел в фоне)
nrb node [--role ...]    headless-узел без движка: ingress | egress | relay | комбинации
nrb deploy user@host     поставить `nrb node` на сервер по SSH
nrb invite / pair        выдать / принять приглашение (ключи, секрет, адрес узла)
```

Сборка узла для VPS: `--no-default-features --features node` → статический musl-бинарь без Servo/GUI
(мегабайты, не сотни). GUI-сборка включает всё. Общий код — крейты ниже.

```
netrunner-browser/
  crates/
    nrb-transport   Transport trait; NrxpTransport (netrunner-core: ClientHandler/Muxer/RawCastFrame);
                    NrxpStream (AsyncRead/Write), NrxpUdpSocket (quinn::AsyncUdpSocket), FakeIpStore
    nrb-net         сетевой сервис: выбор протокола h3/h2/h1, кэш, HSTS, DoH/DNS через туннель,
                    блокировщик (adblock-rust), локальный прокси-слушатель для движка
    nrb-node        роли узла: Ingress (обёртка над ServerHandler), Egress, Relay; LocalAuth;
                    политики egress; reverse-регистрация; реестр своих узлов
    nrb-deploy      russh + SFTP: probe → upload → systemd → firewall → health → rollback
    nrb-engine      trait Engine; impl для Servo (позже — запасной impl)
    nrb-shell       UI: вкладки, omnibox, настройки, менеджер узлов (egui/winit — как servoshell)
    nrb-ext         хост расширений: userscripts, blocking, подмножество WebExtensions
    nrb-profile     закладки, история, загрузки, пароли (шифр. хранилище без системного keyring)
  nrb/              бинарь (clap: browser | node | deploy | invite)
```
`netrunner-core` подключается только из `nrb-transport` и `nrb-node`. Остальное тестируется на
`SystemTransport` (обычные сокеты) — без VPN-ноды.

Предпосылка, которую надо сделать до всего: серверный код лежит в bin-крейте `netrunner-server`
(`server/src/{main,network}.rs`). Чтобы `nrb` мог быть ingress, он должен стать библиотекой
(`netrunner-server-lib`) — это правка в `netrunner-proxy`, а не в новом репо. Без неё MVP может
просто заливать готовый бинарь `netrunner-server` (см. §8).

## 3. Движок: почему теперь Servo

Список «чего не будет» из v0 — WebGL/Canvas, WebRTC, Service Workers, IndexedDB, MSE/видео, iframe и
изоляция процессов, расширения — на Blitz + Boa недостижим: Blitz сам заявляет, что не хочет поддерживать
весь набор браузерных функций, и не имеет JS. Единственный Rust-движок, растущий к полному вебу, — **Servo**
(embeddable-крейт `servo` на crates.io с апреля 2026, релизы ежемесячные, на docs.rs уже 0.7).

| Возможность | Servo сейчас | Что делаем мы |
|---|---|---|
| HTML/CSS/layout, JS (SpiderMonkey) | есть | — |
| iframe, навигация, история | есть | — |
| Canvas 2D, OffscreenCanvas | есть, 2D-рендер многопоточный | — |
| WebGL / WebGPU | есть (WebGPU частично, под prefs) | включаем features, GPU-стек платформы |
| Web Workers / Service Workers | workers есть; SW частично | следим за апстримом, не пишем сами |
| IndexedDB | включается в экспериментальном режиме | включаем pref, хранилище в `nrb-profile` |
| `<video>/<audio>` | через GStreamer (feature `media-gstreamer`) | **GStreamer — системная зависимость**: либо поставляем с бинарём, либо принимаем |
| **MSE** (YouTube-класс видео) | **нет**, проект финансируется с июня 2026 | дыра; закрыть может только апстрим или смена движка |
| WebRTC | зачатки (getUserMedia, 2-way call) | **утечка IP**: ICE открывает свои UDP-сокеты в обход туннеля → по умолчанию выключен, §7 |
| Расширения | **нет** | свой `nrb-ext`, §9 |
| Изоляция процессов | feature `multiprocess` — это не site-per-process | честно: прототип = один процесс + sandbox движка, §6 |
| DRM (Widevine) | нет, и не будет у нас | вне охвата |

Вывод, который надо принять заранее: **«полнофункциональный» = уровень Servo + наши слои.** Мы владеем сетью,
узлами, деплоем, расширениями, оболочкой; веб-совместимость определяет апстрим. Реальный риск — сайты, ломающиеся
на Servo, и отсутствие MSE. Страховка: движок спрятан за `trait Engine`, поэтому при необходимости появляется
второй impl (Chromium/CEF — это уже не «всё на Rust» и не «самодостаточно», решать будете вы по данным прототипа).
Сборка Servo тяжёлая (SpiderMonkey, clang, десятки минут) — закладываем кэш в CI.

## 4. Как весь трафик движка попадает в NRXP

Servo не нужно учить NRXP — нужно, чтобы ему некуда было ходить, кроме нас. Два входа, оба нужны:

* **Режим P (прокси, универсальный).** `nrb-net` слушает на loopback HTTP-CONNECT/SOCKS5 с одноразовым
  логином/паролем на сессию; движку задаём прокси через prefs. Покрывает HTTP, WebSocket, media, workers.
  Браузер делает TLS сам поверх CONNECT-туннеля → поток NRXP (`Connect "host:port"`), DNS резолвит выходная нода.
  Даёт h1/h2. **[проверить]** точные prefs прокси в Servo 0.7 и что они покрывают все пути (workers, media).
* **Режим I (перехват).** `WebViewDelegate::load_web_resource` + `WebResourceLoad::intercept` — встраиватель сам
  отдаёт ответ. Здесь работает `nrb-net` с h3 (quinn + h3 поверх `NrxpUdpSocket`), кэшем, блокировщиком.
  **[проверить]** отдаёт ли `intercept` потоковое тело (иначе большие ответы буферизуются) и видны ли тело/заголовки запроса.
  WebSocket этим путём не идёт — он остаётся на режиме P.

Порядок: сначала P (даёт «всё через NRXP» почти бесплатно), I — как оптимизация ради h3 и политики.

### Транспорт и HTTP/3 (из v0, без изменений по сути)

* Цепочка `packet → tun → nrxp → http/3 → resource` в браузере сворачивается: «пакет» — это QUIC-датаграмма
  quinn, она один-в-один становится кадром `UdpData`; роль TUN играет `trait Transport`. Настоящий OS-TUN нужен
  только на Stage 0 (быстро увидеть страницу через `netrunner-client`).
* `NrxpUdpSocket` реализует `quinn::AsyncUdpSocket`; quinn работает с `SocketAddr`, поэтому host → fake-IP
  (`198.18.x.y`, идея уже есть в `client/src/net/dns.rs::FakeIpStore`), первая датаграмма шлёт `UdpConnect "host:443"`.
* **h3 включаем только если есть нативная datagram-нога.** `Muxer::select_udp_leg` (проверено в
  `core/src/net/connection/muxer.rs`) отдаёт UDP-кадр на datagram-ногу, только если она свежая и кадр влезает в
  `max_datagram_payload`; иначе кадр едет по TCP-ногам, и QUIC получает head-of-line blocking и двойной congestion
  control. Правило: `h3 ⇔ native_datagram_leg && max_datagram ≥ ~1252`, иначе h2 поверх `NrxpStream`. Неизвестный
  origin — гонка h3/h2 с форой 250–300 мс; Alt-Svc и «h3 сработал» запоминаем.
* Одна NRXP-сессия на весь браузер (все вкладки — потоки одного `Muxer`).
* TLS самодостаточный: rustls + `webpki-roots`, без системного хранилища. Отпечаток внутреннего ClientHello (виден
  сайту) — отдельная задача после прототипа.

## 5. Узел: ingress / egress в том же бинаре

### 5.1 Что уже есть в `netrunner-proxy`, а чего нет

| Нужно | Есть | Нет |
|---|---|---|
| Принимать NRXP-клиентов, decoy-fallback для сканеров | `ServerHandler` + `Network` (bin-крейт) | вынести в lib |
| Подключаемая авторизация | трейт `AuthValidator` (`validate`, `report_usage`, `list_mesh_peers`, `validate_mesh_peer`) | реализация без бэкенда → `LocalAuth` |
| Идентичность узла | `Identity`/`LocalIdentity`: секрет + статический X25519, `PROXY_NRXP_STRICT` | генерация и выдача без админки |
| Mesh: ingress строит onion-маршрут через пиров, egress выходит в сеть | `NodeMesh`, `mesh_onion` (HPKE, `MeshPeer{node_id,host,port,decoy_sni,nrxp_secret,nrxp_static_public}`) | — |
| **Egress за NAT** | — (`MeshPeer` — это `host:port`, которое ingress **набирает сам**; поиск `reverse` в `mesh.rs` пуст) | **reverse-регистрация, §5.3** |
| Политика egress (блок private/loopback/link-local) | есть идея в `masque-edge` («rejected by default») | перенести в `nrb-node` |

### 5.2 Роли и политика

* `ingress` — слушает порт, держит decoy, аутентифицирует клиентов. `egress` — выпускает потоки в интернет.
  `relay` — промежуточный хоп mesh. Роли комбинируются; браузер по умолчанию **не** узел (включается явно).
* **`LocalAuth: AuthValidator`** — локальный реестр спаренных устройств: токен ↔ `user_id`, опциональные квоты.
  `report_node_health` — no-op, `list_mesh_peers` — свои узлы из `nrb-profile`. Бэкенд не нужен вовсе;
  опционально позже — регистрация узла в `netrunner-backend` как личного VIP-сервера (упоминаются в
  `nodes/README.md`) — **[проверить]** что этот путь существует для внешних узлов.
* **Egress с пользовательского IP — это ответственность.** Политика по умолчанию: только свои спаренные устройства;
  блок loopback/private/link-local/metadata (иначе чужой клиент попадает в вашу домашнюю сеть); лимиты по
  полосе и числу потоков; без логов трафика; кнопка kill-switch. «Доступ в мою домашнюю сеть со смартфона» —
  отдельный явный режим `lan: allow` для своих устройств, выключен по умолчанию. Режим «чужие пользователи»
  (расшаривание) — вне прототипа: юридически и по абьюзу это другой продукт.

### 5.3 Egress за NAT: reverse-регистрация (новый протокол, главный риск)

Дом/ноутбук обычно не достижим снаружи. Поэтому egress **сам набирает** ingress и держит сессию; ingress
использует её как «ногу» к этому пиру:

```
egress(nrb) ──NRXP, роль «egress-peer», секрет узла──► ingress(VPS)        регистрация, heartbeat
клиент ──► ingress ── mesh-маршрут: Exit через session(egress-peer) ──► кадры Connect/Data вниз по сессии
egress(nrb) обрабатывает их как ServerHandler (открывает сокеты в интернет) и шлёт ответ вверх
```

Нужно в ядре: (а) после хендшейка **поменять роли данных** на этой сессии — дозвонившийся играет серверную сторону
потоков, принявший — клиентскую (`Muxer::new(is_client, …)` уже параметризуется, чётность `stream_id` зависит от
роли); (б) вариант `MeshPeer`, адресуемый не `host:port`, а handle живой входящей сессии (`NodeMesh` кэширует
`PeerSessionKey → MeshPeerSession`); (в) аутентификация регистрации секретом узла и отзыв при разрыве.
**[проверить]** спайком: разделимы ли роли хендшейка (кто ClientHello) и роли потоков в `ServerHandler::run` /
`Muxer`. Запасные варианты, если нет: UPnP/NAT-PMP + явный проброс порта; IPv6; QUIC hole-punching через ingress как
рандеву. Базовый вариант — reverse-сессия, она работает за любым NAT.

## 6. Процессная модель и изоляция

```
 nrb (оболочка/UI) ──┬── netd: NRXP-сессия, nrb-net, локальный прокси, роли узла  (поток → позже процесс)
                     └── engine-host: Servo (WebRender, script, layout)           (процесс, sandbox)
```
* Прототип: engine-host — один дочерний процесс; `multiprocess` Servo включаем позже, но честно называем: это
  разнесение по процессам, а не site-per-process (его в Servo нет — не обещаем).
* **Принцип «у движка нет сети».** engine-host запускается в пустом сетевом пространстве имён (Linux: `unshare
  CLONE_NEWNET`; Windows: AppContainer без network capability; Android: отдельный процесс без `INTERNET`), внутри только
  loopback-релей до `netd` по unix-сокету/fd. Тогда утечка вне туннеля невозможна по построению, а kill-switch —
  свойство, а не код. Это же закрывает сокеты WebRTC и любые обходы прокси-prefs. **[проверить]** что Servo живёт в таком окружении.

## 7. WebRTC и приватность

* По умолчанию WebRTC выключен (pref). Включаемый режим: ICE только relay, STUN/TURN-датаграммы идут как
  `UdpConnect/UdpData` через NRXP; host-кандидаты не раскрываются; зависит от §6 (иначе GStreamer откроет свои сокеты).
* Профиль/хранилище: единый `nrb-profile` (SQLite + шифрование ключом из пароля), без системного keyring.
* Отпечаток: UA/языки/часовой пояс нормализуем под страну выходного узла — после прототипа.

## 8. Деплой на сервер (`nrb deploy`)

Не используем системный `ssh`: клиент на `russh` (+ SFTP) — самодостаточно, одинаково на Linux/Windows/Android.

1. **Подключение.** Ключ или одноразовый пароль (пароль используется один раз для установки ключа и нигде не
   хранится; в `netrunner-backend` провижининг устроен так же). **Отпечаток хоста показываем пользователю и пинним**
   (TOFU с явным подтверждением) — не принимаем молча.
2. **Probe.** `uname -m`, ОС/дистрибутив, systemd, root/sudo, занят ли порт 443, наличие BBR/fq.
3. **Артефакт.** Если архитектура сервера совпадает — заливаем **свой же `nrb`** (musl-сборка узла) по SFTP, без
   сторонних скачиваний. Иначе — подписанный артефакт из релизов, подпись проверяется **на сервере** до запуска
   (ed25519). MVP: заливаем готовый `netrunner-server` из `netrunner-proxy`, пока ingress не вынесен в lib.
4. **Идентичность генерируется на сервере.** Секрет и приватный ключ рождаются там и не передаются; на выходе —
   только публичный ключ и одноразовый токен приглашения (приходят по уже шифрованному SSH-каналу).
5. **Конфиг и сервис.** systemd-юнит с усилением (`NoNewPrivileges`, `ProtectSystem=strict`, `DynamicUser` или
   отдельный пользователь, `AmbientCapabilities=CAP_NET_BIND_SERVICE`), конфиг `0600`, **без логов на диск** (так
   сделано в `netrunner-server`: JSON-лог идёт в stdout, запись на диск ранее забивала диск ноды). Файрвол (ufw/nft):
   открыть только порт узла. Опционально sysctl `bbr` + `fq` (на нодах SG/NL так и стоит, `init_node.sh` их не ставит).
6. **Проверка.** `/health` на loopback ноды и **настоящий NRXP-хендшейк с локальной машины** — «установлено» значит
   «клиент реально подключился». Любой сбой → откат (останов юнита, удаление файлов).
7. **Реестр и приглашения.** Узел заносится в локальный реестр; `nrb invite` выдаёт ссылку/QR вида
   `nrxp://host:port?pk=<static pubkey>&sni=<decoy>&token=<one-time>` — это секрет, срок жизни короткий, токен одноразовый.
8. Идемпотентно: повторный запуск = апгрейд; `nrb node remove` откатывает.

Альтернатива без SSH: команда одной строкой / `docker run` для тех, у кого SSH недоступен.
Что кладём на VPS по умолчанию: **ingress**; затем (отдельный шаг) пользователь включает reverse-egress на домашнем
`nrb`, указывая этот ingress.

## 9. Расширения (`nrb-ext`)

В Servo расширений нет, поэтому по слоям, от дешёвого к дорогому:
1. **Блокировщик** — крейт `adblock` (движок Brave) в `nrb-net`: фильтрует до сети, работает на обоих режимах §4.
2. **Userscripts** — инъекция скриптов через пользовательские скрипты встраивателя Servo. **[проверить]** API.
3. **Подмножество WebExtensions** (manifest v3: content scripts, `storage`, `webRequest`-аналог поверх `nrb-net`,
   `action`, `tabs`) — отдельный большой пласт, после прототипа; совместимость с магазинами не обещаем.

## 11. План: вертикальный срез, от дешёвого к рискованному

| Этап | Результат | Критерий выхода |
|---|---|---|
| **P0** | `servo` в окне `nrb-shell` + `netrunner-client` (OS-TUN): `packet → tun → nrxp` буквально | страница рендерится; сборка Servo воспроизводима в CI |
| **P1** | `nrb-transport` + режим P: прокси на loopback, prefs Servo | трафик идёт без TUN/root; в `tcpdump` нет ничего, кроме NRXP |
| **P2** | `nrb node` ingress в lib + `LocalAuth` + `invite/pair` | второй `nrb` на loopback/в netns ходит через первый, без бэкенда |
| **P3** | `nrb deploy` | с чистого VPS одной командой → клиент подключился через него |
| **P4** | reverse-egress (§5.3) — **спайк начать сразу после P1** | трафик телефона выходит с домашнего IP через VPS-ingress |
| **P5** | `NrxpUdpSocket` + режим I + h3 | h3 vs h2 на одной ноде, откат на h2 при потере datagram-ноги без обрыва вкладки (`scripts/netns-stand/`) |
| **P6** | §6/§7: netns без сети у движка, WebRTC-relay, kill-switch | тест: прямой сокет из engine-host падает; WebRTC не светит реальный IP |
| **P7** | блокировщик, userscripts, закладки/история/загрузки/пароли | — |

Спайки, которые надо закрыть **раньше**, чем строить поверх (каждый — «да/нет» за день-два):
S1 prefs прокси и покрытие в Servo; S2 потоковость `intercept`; S3 разделимость ролей хендшейка и потоков
(reverse-egress); S4 `PROXY_NRXP_STRICT` + секрет реально закрывают ingress без бэкенда (иначе без `--require-auth`
узел — открытый прокси); S5 реальный `max_datagram_payload` ≥ 1252 на живой ноде; S6 Servo в пустом netns.

## 12. Риски (по убыванию)

1. Веб-совместимость и MSE определяет Servo, не мы. 2. Reverse-egress требует правки протокола ядра.
3. Egress с домашнего IP — абьюз/юридическая нагрузка (по умолчанию только свои устройства).
4. Секреты в приглашениях и на VPS (одноразовые токены, генерация на сервере, `0600`).
5. Размер/время сборки Servo; GStreamer как внешняя зависимость.
6. Ingress на VPS — это ещё одна публично видимая точка: decoy и strict-режим обязательны.
